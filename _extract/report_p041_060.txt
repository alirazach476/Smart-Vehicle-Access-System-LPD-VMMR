4.2.2 Testing Methodology     
Evaluation process was done by the following three major phases: Unit Testing, Integration 
Testing and Performance Testing. The modular design provided a good opportunity to test each 
module and the whole system.    
Unit Testing:  In addition to the model specific ones, qualitative end-to-end testing was conducted 
on another set of images and video frames captured from the deployed Orange Pi camera setup. 
• Prior to the system integration, all the software components have been tested individually 
for correctness and performance.    
• A reserved test data set was used to test the YOLOv8n license plate detection model.  
Precision, recall, and mean Average Precision (mAP@0.5) with a confidence threshold of 
0.25 were used to evaluate the detection quality.    
• The adaptive preprocessing module was used for the analysis of images in which bad 
weather (such as night lighting, rain and fog) caused image degradation. Original and 
enhanced images were compared, and the level of improvement in readability of the plates 
as well as visibility of the vehicles was determined.    
• The results of character and digit detection model YOLOv8n were analyzed on cropped 
License Plate Regions. The individual character detection accuracy and the overall plate 
reconstruction accuracy following post processing was used to measure performance.    
• Vehicle classification model EfficientNet-B4 was tested on the entire 17254image test set. 
Different metrics of performance were taken into account including Top-1 accuracy, Top-
5 accuracy, macro precision, macro recall and macro F1-score.    
Integration Testing : After a successful validation of individual modules, the whole recognition 
pipeline was tested as a single system.    
• End-to-end testing was carried out with the images acquired under various weather and 
illumination conditions. The aim was to see that the pre -processing, plate detection, 
character recognition, vehicle classification and authorization components work properly.    
• To validate the edge to cloud communication, the inference was tested on Orange Pi 5 Pro 
and then confirm if the recognition result, authorization decision, and annotated image are 
uploaded to the cloud based dashboard.    \n===== PAGE 42 =====\n

• Different vehicle records were tested with authorization function (allow, deny and 
temporary access). It was found that system decisions were compared to the expected 
outcomes to be able to determine if access-control behavior was correct.    
• Real-time image processing and event synchronization was monitored to ensure the 
results of the recognition performed on the edge devices are reflected in the updates on 
the dashboard.    
Performance Testing : In addition to the model specific ones, qualitative end-to-end testing was 
conducted on another set of images and video frames captured from the deployed Orange Pi 
camera setup.

4.4 Web Dashboard Implementation          
The Web Dashboard is an all -weather smart vehicle gate cloud -based monitoring, 
administration and access-control application for proposed all-weather smart vehicle gate system. 
It has been developed using current web technology stack consisting of both on the front end and 
back end.    
Node.js/Express backend. V ercel is where the application is deployed and it's connected 
to the Orange Pi edge device via a wireless network connection. The results of the edge pipeline 
(license plate text, vehicle make and model predictions, confidence sco re, weather data, 
authorization decisions, time stamps, and compressed annotated image snapshots) are fed in real-
time into the dashboard where they can be visualized and managed.    
The frontend app offers a Live Feed interface, which continually displays the incoming 
recognition events. Each of these events includes details of the license plate detected (image, type, 
etc.), the class of vehicle predicted (car, truck, motorcycle, etc.), confidence values, environmental 
sensing (weather, etc.) and access decision. The dashboard also offers details on gate status, 
showing operators if a barrier is open or closed, following barrier authorization evaluation. 
Administrators can use this interface to see the system in action and take action on any suspicious 
or unusual events.    
A separate administration module for vehicle registration and access management. The 
system database can be populated with authorised vehicles, make and model details. Access 
permissions can be limited to visitor temporary access, permanent deny access or permanent 
access. Entries can be made for a specific period of time and only let visitors into the facility for 
certain time periods. This gives flexibility and at the same time a strict system of access control.    
The dashboard also has an event history that stores all the vehicle detections that have 
been processed and is searchable for auditing and historical analysis purposes. Every entry 
contains the results of the recognition, the results of the attempt to auth orize, the time of the 
recognition and additional information from the inference process. Administrative users can view 
these to see what has happened in the past, to investigate security matters, and to audit system 
activity. In addition, there is a manua l override setting, allowing a person to assume full control 
of the robot in cases where unusual situations arise which cannot be dealt with using automated 
decision making.    
A lightweight vehicle registry, based on JSON data format, is used to manage 
recognition data, which is stored as permanent access -control records. Detection events are kept 
in runtime to update user interface as quickly as possible. Communication between the frontend 
and backend components is done via RESTful API with JSON Web Token (JWT) authentication. 
This architecture guarantees that just legitimate users are able to access administrative functions 
as well as sensitive car data.    \n===== PAGE 49 =====\n 
35    
    
Cloud services integration with edge computing resources is an important aspect of the 
system design. The Orange Pi 5 Pro is used to locally compute all the heavy tasks of AI inference 
models, like license plate detection, character recognition, vehicle classification and authorization 
evaluation. Only processed outputs go to the cloud dashboard, conserving bandwidth and 
respecting user privacy. With this architecture, efficient monitoring and centralized management 
are achieved with site deployment real-time performance.    
The dashboard can also be used for actual gate -control application. The user interface 
will show gate-open and gate-closed events from authorization decisions made by the recognition 
pipeline. These decisions can also be tied to Orange Pi GPIO relay outputs, to directly actuate the 
gate-control hardware if physical barrier automation is required. As such, the dashboard can be 
used not only to monitor access but also as a part of the access-control solution.    
The front end web application has been developed using React 18, TypeScript, Vite and 
Tailwind CSS, the back end is based on a node and express rest API.  
The app is hosted on Vercel, with a single page application (SPA) served on the front 
end, and API endpoints on the back end that handle vehicle registration, event processing, user 
authentication and access-control operations.    
Vehicle registration records are stored in an in -memory data structure for low latency 
updates and a JSON database file (vehicles.json) will contain the records while the system is 
running. Role management is carried out with JWT and authentication and aut horisation is 
implemented. There are two types of user roles: administrator and regular user. The admin has 
more privileges (vehicle registration, user management, manual override, etc.) while normal users 
have less privileges (operational monitoring, visitors).    
For future scalability, the software architecture also features a Supabase PostgreSQL 
Database schema that can deliver persistent cloud storage. The prototype deployed, however, is 
simple and easy to deploy APIs based on express and file storage using json . The gate_sync.py 
utility runs after the inference is completed, and uploads the recognition events to the ingestion 
endpoint on the cloud platform to synchronize the Orange Pi and the cloud platform. This 
mechanism will allow for the information availabl e on the dashboard to be consistent with the 
activities on edge devices.

5.1 License Plate Detection Results          
The first step of the proposed system is to locate the license plates of vehicles in the input images. 
A YOLOv8-Nano (YOLOv8n) object detection model, which has been trained on a locally created 
dataset of Pakistani cars and bikes, is used in this task. The nano version of YOLOv8 was chosen 
because of its lightweight architecture that allows for efficient training and deployment on edge 
devices while maintaining high detection accuracy.    
The detector is a very important preprocessing step, because the subsequent recognition stages are 
all based on correct plate regions. Hence the reliability of this module is directly dependent on its 
accuracy and stability.
